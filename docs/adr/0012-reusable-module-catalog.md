# ADR-0012: Reusable module catalog composed into roadmaps

**Status:** Accepted · Supersedes the roadmap structure described in ADR-0010 (XP amounts and step criteria still apply)

## Context

Roadmaps owned their modules and steps. The same knowledge (e.g. `databases/sql-basics`) appeared as separate steps in up to five roadmaps, so learners re-proved it per roadmap, earned step XP once per copy, and every new roadmap meant copying steps. 86 of the 279 distinct step scopes were duplicated across roadmaps.

## Options considered

1. **Independent roadmaps (status quo).** Simple, but no reuse, duplicated XP and content drift between copies.
2. **Shared catalog only.** Every roadmap is an ordered list of catalog modules; a step is proven once and counts everywhere.
3. **Hybrid: shared catalog + roadmap-specific modules.** Same mechanism as 2, with module *kinds* so roadmaps can still have their own context and a final capstone.

We chose **3**. It keeps one mechanism (modules) while letting role paths stay specific.

## Decision

- **Module** (`LearningModule`): slug, name, description, kind (`Core`, `Context`, `BestPractices`, `Capstone`), category, level, icon, version, published/standalone flags. **ModuleStep**: ordered steps over a topic/subtopic scope with the existing criteria (≥ `MinimumQuestions` distinct questions, ≥ `MinimumAccuracy`% on the latest attempt per question).
- **Roadmap** = ordered `RoadmapModuleLink`s (required or optional). `RoadmapDependency` (percent of another roadmap) is unchanged. `ModuleDependency` is guidance only.
- **Scope uniqueness:** each `(topic, subtopic)` belongs to exactly one published module (enforced by `validate_catalog.py`). Capstones and best-practice packs use their own subtopics.
- **Per-user state:** `UserModuleStepCompletion` (global, permanent), `UserModuleProgress` (started/completed, completed version), `UserRoadmapProgress` (enrolment, counters, completion).

### Progress rules (backend only)

1. Steps inside a module unlock in order; opening a step never completes it.
2. In a roadmap, the first uncompleted required module is current; a required module already started elsewhere is also open; optional modules are always open and never block.
3. Roadmap progress = completed steps of required modules ÷ steps of required modules. A completed module counts as fully done.
4. `AdvanceAsync` runs inside the answer transaction with a fixed number of queries (enrolments, links, module snapshot, latest attempts per topic), completes steps → modules → roadmaps, and enqueues the outbox event (ADR-0009).
5. Starting a roadmap evaluates its modules immediately, so prior knowledge and shared modules are credited; the response reports `alreadyCompletedModules` / `alreadyCompletedSteps`.

### XP rules

- Step XP: once per user and step (on the first completion row).
- Module XP: once per user and module (when `UserModuleProgress.CompletedAt` is first set).
- Roadmap XP: once per user and roadmap — finishing a second roadmap pays its own bonus even if all its modules were done before.
- Credits mapped from legacy data are stored with `XpAwarded = false` and pay nothing.

### Versioning

Adding steps to a module that already has steps increments `Version`; new steps record `AddedInVersion`. Completions are permanent: `CompletedVersion` records what the learner completed, newer steps are shown as "new content", and nothing revokes a completion or XP.

### Seed and migration

- `modules.json` (catalog) and `roadmaps.json` (composition only) are generated by `scripts/seed-src/modules.py` / `roadmaps.py` and checked by `validate_catalog.py` in CI.
- The seeder inserts missing modules/steps, follows the seed for seed-managed modules and compositions, and never overwrites admin edits (`SeedManaged`, `CompositionSeedManaged`).
- Migration `ReusableModuleCatalog` converts every old roadmap module/step into a catalog module/step **with the same id** (so completions, current steps, practice sessions, XP ledger entries and translations stay valid), then the seeder re-composes roadmaps from the curated catalog, hides orphan legacy modules and credits legacy completions by scope.

## Consequences

- Knowledge is proven once; XP can no longer be farmed by duplicated steps.
- Roadmaps that now include whole shared modules can have a few more steps than before (394 → 449 steps across the 32 existing roadmaps); completions are never lost.
- Authoring a roadmap means composing modules; new knowledge needs a new subtopic (scope) and questions. See `scripts/seed-src/CATALOG_AUTHORING.md`.
- The progress engine and its pure rules (`RoadmapComposition`) are unit-tested; shared credit, XP-once, optional modules and the data migration have integration tests.
